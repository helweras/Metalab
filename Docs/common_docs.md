# MetaLab — техническая документация

## 1. Описание проекта

**MetaLab** — экспериментальная платформа для моделирования боёв между агентами с различными характеристиками и стратегиями поведения.

Основная цель проекта — исследовать эффективность различных сборок и стратегий, проводить серии испытаний и в дальнейшем автоматизировать поиск эффективных конфигураций.

На начальном этапе проект реализуется как консольная библиотека без CLI.

### Технологии

- Python 3.12
- uv — управление окружением и зависимостями
- pytest — тестирование
- Ruff — проверка и форматирование кода
- Git — контроль версий

## 2. Основные сущности

### 2.1. Build

`Build` — неизменяемая модель данных, описывающая начальные характеристики агента.

Характеристики:
- `health` — здоровье;
- `damage` — урон.

Правила сборки:
- Базовое значение каждой характеристики — 1.
- Дополнительный бюджет — 10 очков.
- Стоимость увеличения каждой характеристики на единицу — 1 очко.
- Неиспользованные очки разрешено оставлять.
- Минимальное значение каждой характеристики — 1.
- Максимальная сумма характеристик — 12.

Ответственность:
- хранить значения характеристик;
- проверять типы данных;
- проверять минимальные значения;
- проверять, что сумма характеристик не превышает допустимый максимум;
- обеспечивать неизменяемость объекта.

`Build` не отвечает за распределение бюджета и не знает, каким способом были получены значения характеристик.

### 2.2. BuildGenerator

`BuildGenerator` — компонент, отвечающий за формирование сборок на основании правил распределения очков.

Его задача — проверять корректность распределения бюджета и создавать объекты `Build`.

В отличие от `Build`, который проверяет допустимость готовых характеристик, `BuildGenerator` проверяет соблюдение правил формирования сборки.

Возможные варианты реализации в будущем:
- ручное распределение очков;
- случайная генерация;
- генерация по заданным ограничениям;
- алгоритмический поиск эффективных сборок.

**Текущий статус:** не реализован.

До появления генератора сборки можно создавать напрямую через `Build(health=..., damage=...)`.

При этом `Build` проверяет только допустимость итоговых характеристик. Он не подтверждает, что распределение было выполнено по правилам бюджета. Поэтому ручное создание подходит для текущей разработки, но не заменяет полноценную проверку распределения.

### 2.3. Agent

`Agent` — боевой участник, созданный на основании `Build`.

Ответственность:
- хранить ссылку на исходную сборку;
- хранить текущее здоровье и урон;
- предоставлять доступ к текущим характеристикам;
- изменять собственное здоровье;
- определять, жив ли агент.

Особенности:
- начальные характеристики копируются из `Build`;
- изменения боевого состояния не изменяют исходную сборку;
- агент не выбирает стратегию;
- агент не управляет ходом боя.

### 2.4. AgentState

`AgentState` — неизменяемый снимок состояния обоих участников на момент принятия решения.

Предполагаемые поля:
- `own_health` — текущее здоровье своего агента;
- `own_damage` — текущий урон своего агента;
- `opponent_health` — текущее здоровье противника;
- `opponent_damage` — текущий урон противника;
- `round_number` — номер текущего раунда.

Ответственность:
- предоставлять стратегии необходимые сведения для принятия решения;
- обеспечивать неизменность информации на протяжении выбора действий.

`AgentState` формируется `BattleEngine`.

Оба снимка должны быть сформированы до вызова стратегий, чтобы действия обоих участников выбирались на основании одного и того же состояния боя.

В дальнейшем состав доступных данных может различаться в зависимости от правил видимости информации.

### 2.5. Action

`Action` — неизменяемое описание действия, выбранного стратегией.

Может содержать:
- тип действия;
- параметры действия;
- выбранные модификаторы.

Ответственность:
- описывать намерение агента;
- передавать параметры выбранного действия движку.

`Action` не выполняет действие самостоятельно, не изменяет характеристики агента и не управляет боем.

Интерпретация действия и расчёт его последствий выполняются `BattleEngine`.

### 2.6. AgentStrategy

`AgentStrategy` — алгоритм принятия решений агентом.

Ответственность:
- получать `AgentState`;
- анализировать состояние своего агента и противника;
- выбирать действие;
- формировать и возвращать `Action`.

Предполагается возможность создания различных стратегий с единым интерфейсом.

Стратегия не должна напрямую изменять состояние агента или управлять ходом боя.

### 2.7. BattleEngine

`BattleEngine` — основной компонент, управляющий процессом боя.

Ответственность:
- принимать двух агентов и их стратегии;
- формировать снимки `AgentState`;
- получать действия от обеих стратегий;
- интерпретировать `Action`;
- рассчитывать последствия действий;
- применять последствия раунда одновременно;
- контролировать завершение боя;
- формировать результат боя.

Движок является единственным компонентом, управляющим последовательностью боя.

### 2.8. BattleResult

`BattleResult` — модель данных, описывающая результат завершённого боя.

Должна содержать информацию, необходимую для определения исхода:
- победитель или победители;
- проигравший или проигравшие;
- количество проведённых раундов;
- причину завершения боя.

Если оба агента погибают в одном раунде, оба считаются проигравшими.

Если оба остаются живы после достижения лимита раундов, оба считаются победителями.

### 2.9. ExperimentRules

`ExperimentRules` — регламент проведения серии испытаний.

Может определять:
- максимальное количество раундов;
- условия проведения испытаний;
- параметры серии боёв.

Лимит раундов относится к регламенту испытаний, а не к постоянным характеристикам отдельного боя.

### 2.10. BuildStorage

`BuildStorage` — компонент для сохранения и загрузки сборок.

Ответственность:
- сохранять сборки;
- загружать ранее сохранённые сборки;
- обеспечивать восстановление объектов `Build`.

Формат хранения будет определён позднее. Один из возможных вариантов — JSON.

### 2.11 ActionRegistry

Реестр доступных игровых действий. Отвечает за хранение описаний действий и предоставление `AgentStrategy` набора доступных вариантов для выбора. В перспективе может учитывать ограничения, связанные с характеристиками агента, экипировкой и способностями.

В MVP содержит только действие атаки.

## 3. Правила проведения боя

### 3.1. Последовательность раунда

1. `BattleEngine` получает текущее состояние обоих агентов.
2. Формирует два объекта `AgentState`.
3. Передаёт соответствующий снимок каждой стратегии.
4. Получает оба объекта `Action`.
5. Рассчитывает последствия обоих действий.
6. Применяет последствия одновременно.
7. Проверяет состояние обоих агентов.
8. Определяет, завершён ли бой.

### 3.2. Одновременность действий

Оба агента выбирают действия до применения последствий раунда.

Каждый агент наносит полный урон, рассчитанный на основании состояния в начале раунда.

Если агент погибает в результате текущего раунда, он всё равно совершает уже выбранное действие.

### 3.3. Условия завершения боя

| Ситуация | Результат |
|---|---|
| Погиб только первый агент | Победа второго |
| Погиб только второй агент | Победа первого |
| Погибли оба агента | Оба проиграли |
| Оба живы после достижения лимита раундов | Оба победили |

Проценты оставшегося здоровья не сравниваются.

## 4. Архитектурные принципы

При разработке необходимо придерживаться следующих принципов:

- **SRP:** каждый компонент отвечает за одну область ответственности.
- **Инкапсуляция:** внешние компоненты не должны напрямую изменять внутреннее состояние агента.
- **Неизменяемость:** конфигурации сборок, снимки состояния и описания действий должны быть неизменяемыми.
- **Разделение данных и логики:** модели данных не должны самостоятельно управлять игровым процессом.
- **Расширяемость:** новые стратегии и типы действий должны добавляться без необходимости переписывать основные компоненты движка.

## 6. Тестирование

Каждый компонент должен иметь отдельные тесты.

Основные требования:
- проверка корректного создания объектов;
- проверка граничных значений;
- проверка обработки некорректных данных;
- проверка неизменяемости там, где она предусмотрена;
- проверка независимости компонентов;
- проверка правил одновременного проведения боя.

После реализации основных компонентов необходимо провести интеграционное тестирование полного цикла боя.

## 7. Ограничения текущего этапа

На этапе MVP не реализуются:
- способности и сложные модификаторы;
- автоматическая генерация сборок;
- оптимизационный поиск сборок;
- обучение стратегий;
- сложные форматы турниров;
- CLI;
- расширенная система хранения результатов.

Эти возможности рассматриваются как дальнейшее развитие проекта.


## Новые сущности боевой системы

### ActionResult

**Назначение:** хранение результата обработки конкретного действия.

Содержит информацию о фактическом результате действия после обработки входящего воздействия получателем.

Используется для:
- передачи результатов действия системе обработки способностей;
- расчёта дополнительных эффектов, зависящих от результата действия;
- фиксации фактического результата атаки.

Пример: агент отправил 3 единицы урона, но после обработки защиты противника фактически нанесено 2 единицы. `ActionResult` должен отражать фактический результат, а не первоначальную величину воздействия.

Состав полей пока не определён.

### Effect

**Назначение:** описание игрового воздействия, формируемого действием или способностью.

Возможные виды:
- урон;
- восстановление здоровья;
- изменение характеристик;
- другие игровые воздействия.

Основные обязанности:
- хранить параметры воздействия;
- передавать информацию о воздействии получателю;
- не изменять состояние агента самостоятельно.

`Effect` отделяет описание воздействия от механизма его обработки.

### Обработка входящих эффектов

Получатель обрабатывает входящий эффект с учётом собственных характеристик и действующих модификаторов.

В результате обработки определяется фактический результат воздействия, который фиксируется в `ActionResult`.

На текущем этапе отдельный `EffectProcessor` не создаётся. Обработку координирует `BattleEngine`. Возможность выделения отдельного компонента рассматривается при усложнении системы.

### Обновлённая роль BattleEngine

`BattleEngine` координирует последовательность боевого раунда:

1. Формирует снимки состояний агентов.
2. Передаёт снимки стратегиям для выбора действий.
3. Получает выбранные действия обоих агентов.
4. Организует формирование исходящих эффектов.
5. Организует обработку входящих эффектов.
6. Получает результаты обработки в виде `ActionResult`.
7. Организует расчёт дополнительных эффектов способностей на основании полученных результатов.
8. Применяет все рассчитанные изменения после завершения расчётов текущего раунда.
9. Проверяет условия завершения боя.

Движок отвечает за координацию процесса, но не должен содержать реализацию каждого отдельного игрового правила.

### Принцип обработки раунда

Все результаты действий и дополнительных эффектов текущего раунда должны быть рассчитаны до применения изменений к состояниям агентов.

Это обеспечивает независимость результата от порядка обработки участников и позволяет обоим агентам завершить уже выбранные действия, даже если один из них погибает в этом раунде.

### Актуальные архитектурные решения

| Сущность | Статус |
|---|---|
| `Effect` | Концепция принята, реализация отложена |
| `ActionResult` | Концепция принята, состав полей открыт |
| `EffectProcessor` | Отложен, пока обработку координирует `BattleEngine` |
| Обработка способностей | Координируется `BattleEngine`, отдельный компонент пока не создаётся |
