# MetaLab — техническая документация

## 1. Архитектура проекта

MetaLab — платформа моделирования боёв между агентами.

Архитектура разделяет:
- конфигурацию агентов;
- текущее состояние агентов;
- принятие решений;
- описание действий;
- правила расчёта последствий;
- применение последствий;
- управление ходом боя.

Основной принцип: стратегия определяет, какое действие выполнить, правила рассчитывают последствия, а движок управляет исполнением и изменением состояния участников.

## 3. Модели данных

### 3.1. Build

Назначение: неизменяемая конфигурация исходных характеристик агента.

Реализация:
- `dataclass(frozen=True)`;
- характеристики представлены отдельными полями;
- текущие значения характеристик в Build не хранятся.

Текущие характеристики:
- `health`;
- `damage`.

Ограничения:
- начальные значения обеих характеристик равны 1;
- дополнительный бюджет составляет 10 очков;
- стоимость единицы характеристики — 1;
- неиспользованные очки разрешено сохранять;
- максимальная сумма характеристик — 12.

Build отвечает только за хранение и валидацию готовой конфигурации. Распределение бюджета не входит в его ответственность.

### 3.2. Attribute

Назначение: идентификатор характеристики агента.

Текущие значения:
- `HEALTH`;
- `DAMAGE`.

Используется как ключ при хранении и изменении характеристик.

### 3.3. Agent

Назначение: представление участника боя и управление его текущим состоянием.

При создании получает Build и формирует собственное хранилище текущих характеристик.

Структура текущих характеристик:

```python
dict[Attribute, int]
```

Основные обязанности:
- хранение исходной конфигурации Build;
- хранение текущих характеристик;
- получение значения характеристики;
- универсальное изменение характеристики;
- определение жизнеспособности агента.

Основные операции:

```python
get_attribute(attribute: Attribute) -> int

apply_change(attribute: Attribute, value: int) -> None
```

`apply_change` принимает дельту:
- положительное значение увеличивает характеристику;
- отрицательное уменьшает;
- ноль не изменяет её.

Текущее состояние не должно изменяться напрямую извне Agent.

### 3.4. AgentSnapshot

Назначение: неизменяемый снимок текущих характеристик агента.

Структура:

```python
@dataclass(frozen=True)
class AgentSnapshot:
    attributes: Mapping[Attribute, int]
```

Для обеспечения независимости снимка:
- создаётся копия исходного словаря;
- копия оборачивается в `MappingProxyType`;
- изменение исходного словаря не влияет на снимок;
- изменение характеристик через снимок невозможно.

Snapshot не содержит логики изменения характеристик.

### 3.5. AgentState

Назначение: представление состояния участников для принятия решений и расчёта действий.

Структура:

```python
@dataclass(frozen=True)
class AgentState:
    own_state: AgentSnapshot
    enemy_state: AgentSnapshot
```

Содержит:
- снимок собственного состояния;
- снимок состояния противника.

AgentState не владеет состояниями агентов и не изменяет их.

### 3.6. Action

Назначение: описание выбранного агентом действия.

Структура:

```python
@dataclass(frozen=True)
class Action:
    action_type: ActionType
    target: Target
```

Action описывает намерение, но не содержит алгоритма выполнения.

### 3.7. ActionType

Назначение: идентификатор типа действия.

Текущие значения:
- `ATTACK`.

Используется ActionRegistry для определения соответствующих правил.

### 3.8. Target

Назначение: определение цели выбранного действия.

Текущие значения:
- `SELF`;
- `ENEMY`.

Используется стратегией при формировании Action и передаётся правилам действия.

### 3.9. ActionResult

Назначение: описание изменения одной характеристики.

Структура:

```python
@dataclass(frozen=True)
class ActionResult:
    attribute: Attribute
    value: int
```

`value` представляет дельту характеристики, а не её итоговое значение.

Один ActionResult описывает изменение только одной характеристики.

Одно действие может иметь несколько результатов, поэтому используется кортеж.

### 3.10. Effect

Назначение: описание результата воздействия и агента, к которому он должен быть применён.

Предполагаемая структура:

```python
@dataclass(frozen=True)
class Effect:
    result: ActionResult
    target: Target
```

Effect объединяет:
- описание изменения;
- получателя изменения.

Одно действие может возвращать несколько Effect, в том числе направленных разным участникам боя.

Effect не выполняет изменение самостоятельно.

### 3.11. EffectTarget

Предусмотрен как возможное отдельное перечисление для определения получателей эффектов.

В текущей реализации не используется.

Пока Effect использует общий Target. Разделение типов оправданно только при появлении самостоятельной семантики целей действия и получателей эффектов.

## 4. Механика действий

### 4.1. ActionRules

Назначение: контракт для реализации правил конкретных типов действий.

Абстрактный базовый класс:

```python
class ActionRules(ABC):

    @abstractmethod
    def rule(
        self,
        state: AgentState,
        target: Target
    ) -> tuple[Effect, ...]:
        ...
```

Правила:
- получают состояние участников на момент расчёта;
- получают выбранную цель действия;
- рассчитывают последствия;
- возвращают кортеж Effect.

ActionRules не должны:
- самостоятельно изменять Agent;
- управлять ходом боя;
- определять порядок выполнения действий;
- зависеть от BattleEngine.

### 4.2. Конкретные правила

Для каждого типа действия предусматривается собственная реализация ActionRules.

Например:

```text
AttackRules(ActionRules)
```

AttackRules отвечает за расчёт последствий атаки.

Правила используют переданный AgentState, поэтому одна реализация может применяться ко всем агентам. Результат зависит от характеристик участников, а не от отдельного экземпляра правил.

Новые типы действий добавляются через новые реализации ActionRules.

### 4.3. ActionRegistry

Назначение: сопоставление ActionType с соответствующими реализациями ActionRules.

Реестр является общим для участников одного боя, поскольку все агенты используют одинаковые правила действий.

Логическое сопоставление:

```text
ATTACK -> AttackRules
```

Обязанности:
- хранение зарегистрированных правил;
- получение реализации правил по ActionType;
- предоставление правил BattleEngine.

Реестр не рассчитывает последствия и не применяет эффекты.

## 5. BattleEngine

Назначение: управление процессом боя и координация взаимодействия остальных компонентов.

BattleEngine отвечает за:
- взаимодействие двух агентов;
- получение состояний участников;
- передачу состояний стратегиям;
- получение выбранных действий;
- поиск соответствующих ActionRules через ActionRegistry;
- расчёт последствий действий;
- применение полученных Effect;
- проверку условий завершения боя;
- формирование результата боя.

### 5.1. Общая последовательность выполнения

```text
Agent A                 BattleEngine                 Agent B
   |                         |                           |
   |<------ AgentState ------|                           |
   |                         |------ AgentState -------->|
   |                         |                           |
   |------ Action ---------->|                           |
   |                         |<--------- Action ---------|
   |                         |                           |
   |                  ActionRegistry                     |
   |                         |                           |
   |                  Получение Rules                    |
   |                         |                           |
   |                  Расчёт Effect                      |
   |                         |                           |
   |                  Применение Effect                  |
   |                         |                           |
   |                  Проверка окончания                 |
```

### 5.2. Правила выполнения боя

Для MVP определены следующие правила:

1. Бой состоит из последовательных раундов.
2. Оба агента выбирают действия до применения последствий.
3. Оба действия рассчитываются относительно состояния на начало раунда.
4. Последствия обоих действий применяются одновременно.
5. Агент, погибший в текущем раунде, всё равно совершает выбранное действие.
6. Если оба агента погибают в одном раунде, оба проигрывают.
7. Если погибает один агент, второй побеждает.
8. Если оба агента остаются живы после достижения лимита раундов, оба признаются победителями.
9. Проценты оставшегося здоровья между агентами не сравниваются.

### 5.3. Применение Effect

BattleEngine определяет получателя каждого эффекта:

```python
if effect.target == Target.SELF:
    target_agent = acting_agent
else:
    target_agent = enemy_agent
```

Затем применяет изменение:

```python
target_agent.apply_change(
    effect.result.attribute,
    effect.result.value
)
```

Важно: при одновременном выполнении действий движок должен сначала рассчитать последствия обоих действий, а затем применить их. Нельзя применять первое действие до расчёта второго, иначе второе будет рассчитано уже по изменённому состоянию.

## 6. Основные зависимости компонентов

```text
Build
  |
  v
Agent
  |
  v
AgentSnapshot
  |
  v
AgentState
  |
  +--------------------+
  |                    |
  v                    v
AgentStrategy       ActionRules
  |                    ^
  v                    |
Action                 |
  |                    |
  v                    |
ActionType             |
  |                    |
  v                    |
ActionRegistry --------+
  |
  v
BattleEngine
  |
  v
Effect
  |
  v
ActionResult
  |
  v
Agent.apply_change()
```

Схема показывает основные связи, а не полный граф импортов. BattleEngine координирует компоненты, но не должен содержать реализацию конкретных правил действий.

## 7. Архитектурные ограничения

При дальнейшем развитии проекта следует сохранять следующие принципы:

1. Build не отвечает за текущее состояние агента.
2. Agent является единственным владельцем изменяемых текущих характеристик.
3. Snapshot и AgentState не должны предоставлять возможность изменения состояния.
4. Strategy выбирает действия, но не выполняет их.
5. Action описывает намерение, но не содержит механики.
6. ActionRules рассчитывает последствия, но не применяет их.
7. Effect описывает изменение и его получателя.
8. ActionRegistry связывает тип действия с правилами.
9. BattleEngine управляет исполнением и применением последствий.
10. Конкретные правила действий не должны зависеть от конкретных агентов.

## 8. Компоненты, требующие дальнейшей разработки

На текущем этапе не следует считать завершёнными:

- конкретные реализации ActionRules, включая AttackRules;
- окончательную реализацию ActionRegistry;
- AgentStrategy и конкретные стратегии;
- BattleEngine;
- модель результата боя;
- правила завершения и ограничения боя в виде отдельной конфигурации;
- историю раундов и действий.

Новые абстракции вводятся по мере появления конкретных требований, а не только ради потенциального расширения.
