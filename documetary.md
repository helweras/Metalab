# MetaLab — концепция проекта

## 1. Назначение проекта

MetaLab — экспериментальная платформа для моделирования боёв между агентами с различными характеристиками и стратегиями поведения.

Основная задача проекта — исследовать эффективность различных сборок и стратегий агентов.

В перспективе проект должен поддерживать автоматическую генерацию сборок и обучение агентов. Эти возможности не входят в первый MVP.

## 2. Основные сущности

### Build

`Build` — конфигурация агента.

Ответственность:
- хранение характеристик сборки;
- предоставление данных для создания агента.

Особенности:
- сборка не изменяется во время боя;
- одна сборка может использоваться для создания нескольких агентов;
- повреждение агента не должно изменять исходную сборку;
- предполагается использование `dataclass`.

### Agent

`Agent` — участник конкретного боя.

Ответственность:
- хранение текущего боевого состояния;
- предоставление доступа к текущим характеристикам;
- принятие решений о собственных действиях;
- передача выбранных действий боевому движку.

Агент самостоятельно принимает решения, но не применяет их последствия к противнику.

### Action

`Action` — отдельная сущность, представляющая действие, выбранное агентом.

Ответственность:
- представление принятого агентом решения;
- передача информации о действии боевому движку.

`Action` описывает действие, но самостоятельно его не выполняет.

### BattleEngine

`BattleEngine` — компонент, управляющий боевым процессом.

Ответственность:
- управление раундами;
- получение действий от агентов;
- обработка действий;
- применение последствий действий к участникам;
- контроль условий завершения боя;
- определение результата боя.

Движок не должен самостоятельно принимать тактические решения вместо агентов.

## 3. Характеристики сборки

На первом этапе используются две характеристики:

- `health` — здоровье;
- `damage` — наносимый урон.

Начальные значения:
- здоровье: 1;
- урон: 1.

Дополнительный бюджет: 10 очков.

Правила распределения:
- бюджет можно произвольно распределять между здоровьем и уроном;
- стоимость дополнительной единицы каждой характеристики составляет 1 очко;
- базовые значения не входят в дополнительный бюджет;
- допускается не расходовать весь бюджет;
- стоимость характеристик должна допускать независимую настройку в будущем.

Пример сборки:
- здоровье: 8;
- урон: 4.

В этом примере использовано 10 дополнительных очков.

Способности и дополнительные механики не входят в первый MVP.

## 4. Правила дуэли

### Общие правила

- Бой состоит из последовательных раундов.
- В бою участвуют два агента.
- Оба агента получают одинаковое количество ходов.
- Агенты принимают решения до применения последствий действий текущего раунда.
- Движок получает решения обоих агентов.
- Последствия действий применяются одновременно.
- Порядок обработки участников не должен влиять на результат боя.

### Обработка раунда

1. Оба агента получают доступную им информацию и принимают решения.
2. Каждый агент формирует `Action`.
3. Движок получает действия обоих агентов.
4. Движок обрабатывает действия.
5. Последствия действий применяются одновременно.
6. Проверяются условия завершения боя.

Таким образом, даже если один агент погибает в результате текущего раунда, он всё равно успевает совершить действие, принятое до применения последствий этого раунда.

### Завершение боя

- Если оба агента погибли — оба проиграли.
- Если погиб один агент — второй победил.
- Если оба агента выжили после достижения лимита раундов — оба победили.

### Лимит раундов

- Лимит раундов задаётся регламентом серии испытаний.
- Лимит не является постоянной характеристикой отдельной дуэли.
- Движок должен получать соответствующие правила извне.

## 5. Серии испытаний

Серия испытаний позволяет проводить бои между участниками по заданному регламенту.

Для первого MVP:
- при наличии двух участников проводится один бой;
- лимит раундов задаётся до начала серии.

Более сложные форматы серий пока не определены.

## 6. Создание и хранение сборок

- Сборки создаются вручную.
- Сборки сохраняются в файлах.
- Сохранённые сборки можно повторно использовать.
- Формат хранения пока не определён.
- Использование базы данных на первом этапе не требуется.

Формат журнала боя и хранения результатов пока не определён.

## 7. Технологический стек

- Python 3.12
- uv — управление окружением и зависимостями.
- pytest — тестирование.
- Ruff — контроль качества и стиля кода.
- Git — контроль версий.
- PyCharm — среда разработки.

На первом этапе взаимодействие с программой будет осуществляться через Python-интерпретатор. CLI пока не реализуется.

## 8. Принципы разработки

- Соблюдать принципы SOLID там, где они оправданы архитектурой.
- Разделять конфигурацию, боевое состояние, принятие решений и исполнение действий.
- Не смешивать ответственность агентов и боевого движка.
- Предусматривать возможность расширения механики без преждевременной реализации будущих функций.
- Покрывать функциональность тестами по мере разработки.
- Проверять отдельные компоненты и взаимодействие между ними.
- Не добавлять абстракции без практической необходимости.
