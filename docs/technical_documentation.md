# Техническая документация MetaLab

## 1. Назначение проекта

MetaLab — Python-проект для моделирования пошаговых боёв между двумя агентами. Агент создаётся на основе неизменяемой сборки характеристик (*Build*) и действует согласно переданной стратегии (*AgentStrategy*).

Текущая реализация поддерживает:
- характеристики здоровья и урона;
- одно действие — атаку;
- выбор цели: сам агент или противник;
- расчёт эффектов отдельно от их применения;
- завершение боя по смерти участников или достижению лимита раундов;
- возврат итогового результата боя со снимками состояний участников.

Система пока является базовым боевым симулятором. Генерация сборок, полноценный выбор стратегии, массовые эксперименты, сохранение результатов и обучение агентов в коде не реализованы.

## 2. Технологии и запуск

- Python: 3.12 или новее.
- Управление окружением и зависимостями: uv.
- Тестирование: pytest.
- Проверка и форматирование кода: Ruff.

Установка зависимостей разработки:

```bash
uv sync --group dev
```

Запуск тестов:

```bash
uv run pytest
```

Проверка кода:

```bash
uv run ruff check .
uv run ruff format --check .
```

Автоматическое исправление поддерживаемых замечаний и форматирование:

```bash
uv run ruff check . --fix
uv run ruff format .
```

В `pyproject.toml` настроены правила Ruff: `E`, `F`, `I`, `B`, `UP`; длина строки — 88 символов. В runtime-зависимостях проекта сейчас нет сторонних пакетов. pytest и Ruff находятся в группе dev.

В проекте также объявлена команда `metalab`, указывающая на `metalab:main`. Текущая функция `main()` в `src/metalab/__init__.py` выводит приветственное сообщение; полноценного CLI пока нет.

## 4. Основные сущности

### 4.1. Attribute

Модуль: `attribute.py`

Перечисление характеристик агента:

- `Attribute.HEALTH` — здоровье;
- `Attribute.DAMAGE` — урон.

Текущие характеристики агента хранятся в словаре, ключами которого являются значения `Attribute`.

### 4.2. Build

Модуль: `build.py`

Неизменяемая сборка агента:

- `damage` — исходное значение урона;
- `health` — исходное значение здоровья.

Класс реализован как `@dataclass(frozen=True)`. Проверка в `__post_init__` требует, чтобы оба значения имели точный тип `int`, были больше нуля и в сумме не превышали `MAX_BUILD_POINTS`.

Константы находятся в `const/build_const.py`:

- `BASE_HEALTH = 1`;
- `BASE_DAMAGE = 1`;
- `BUILD_POINTS = 10`;
- `MAX_BUILD_POINTS = 12`.

Build валидирует уже переданные значения. Распределением бюджета между характеристиками он не занимается.

### 4.3. Agent

Модуль: `agent.py`

Agent — изменяемый участник боя. Он создаётся из Build и хранит ссылку на исходную сборку, а также текущие характеристики:

- начальное здоровье берётся из `build.health`;
- начальный урон берётся из `build.damage`.

Основные элементы API:

- `is_alive` — свойство, возвращающее `True`, если текущее здоровье больше нуля;
- `snapshot` — свойство, создающее неизменяемый снимок текущих характеристик;
- `apply_action_result(action_result)` — применяет изменение одной характеристики.

Для здоровья реализовано верхнее ограничение: лечение не может поднять здоровье выше значения `build.health`. Нижнее ограничение в текущем коде не применяется: здоровье может стать отрицательным. Это соответствует текущим тестам, включая проверку результата `-1`.

### 4.4. AgentSnapshot

Модуль: `agent_snapshot.py`

Неизменяемый снимок характеристик агента. Поле `attributes` аннотировано как `Mapping[Attribute, int]`.

В `__post_init__` создаётся копия переданного словаря, после чего она оборачивается в `MappingProxyType`. Поэтому последующие изменения исходного словаря не меняют снимок, а изменить отображение через снимок нельзя.

Snapshot используется для передачи состояния стратегиям и для сохранения итогового состояния боя.

### 4.5. AgentPerspective

Модуль: `agent_perspective.py`

Неизменяемый объект, описывающий состояние боя с позиции одного участника:

- `own_state` — снимок самого агента;
- `enemy_state` — снимок противника.

Оба поля проверяются на принадлежность к типу AgentSnapshot. В начале каждого раунда BattleEngine создаёт две перспективы из одних и тех же снимков: одну для A, другую для B.

## 5. Действия и эффекты

### 5.1. ActionType и Target

Модули: `action_type.py`, `target.py`

`ActionType` определяет тип действия. Сейчас доступно только `ATTACK`.

`Target` задаёт получателя эффекта:
- `SELF` — сам действующий агент;
- `ENEMY` — противник.

Список доступных стратегии действий задан в `const/action_const.py` как `AVAILABLE_ACTIONS`. Сейчас он формируется из всех элементов ActionType.

### 5.2. Action

Модуль: `action.py`

Неизменяемое описание выбранного действия. Содержит:
- `action_type`;
- `target`.

Action описывает намерение стратегии, но не реализует механику выполнения. Типы обоих полей проверяются при создании объекта.

### 5.3. ActionResult

Модуль: `action_result.py`

Неизменяемое изменение одной характеристики:
- `attribute` — изменяемая характеристика;
- `value` — целочисленная дельта.

Положительное значение увеличивает характеристику, отрицательное уменьшает, ноль не меняет её. ActionResult не определяет, какому агенту адресовано изменение.

### 5.4. Effect

Модуль: `effect.py`

Effect связывает ActionResult с получателем:
- `action_result` — изменение характеристики;
- `target` — получатель, по умолчанию `Target.ENEMY`.

Effect — описание рассчитанного результата. Сам по себе он не изменяет состояние Agent.

### 5.5. ActionRules и AttackRules

Модули: `action_rules/base.py`, `action_rules/attack.py`

`ActionRules` — абстрактный базовый класс. Реализации должны предоставить метод:

`calculate_effects(state, target) -> tuple[Effect, ...]`

Метод получает перспективу действующего агента и выбранную цель, после чего возвращает набор эффектов. Он рассчитывает изменения, но не применяет их.

`AttackRules` реализует атаку:
1. получает урон действующего агента из `state.own_state`;
2. создаёт отрицательную дельту здоровья;
3. возвращает один Effect с указанной целью.

Таким образом, урон атакующего определяется его собственной характеристикой DAMAGE, а получатель задаётся Target.

### 5.6. ActionRulesRegistry

Модуль: `action_rules_registry.py`

Реестр связывает ActionType с реализацией ActionRules. Сейчас в нём зарегистрирован `AttackRules` для `ActionType.ATTACK`.

Метод `get(action_type)` возвращает соответствующие правила. Если ключ не зарегистрирован, словарь выбросит KeyError.

## 6. Стратегия агента

Модуль: `agent_strategy.py`

`AgentStrategy` получает кортеж доступных действий в конструкторе. Метод `choose_action(own_perspective)` возвращает объект Action.

Текущая реализация:
- выбирает первый элемент `available_actions`;
- для ATTACK назначает цель ENEMY;
- для неподдерживаемого типа действия выбрасывает ValueError.

Это минимальная реализация-заглушка. В текущем конструкторе нет проверки пустого кортежа или типов его элементов: пустой кортеж приведёт к IndexError при выборе действия.

Стратегия получает AgentPerspective, а не сам Agent. Это отделяет принятие решения от прямого доступа к изменяемому объекту участника.

## 7. Настройки и правила боя

### 7.1. BattleSettings

Модуль: `battle_settings.py`

Неизменяемая конфигурация боя. Сейчас содержит только `max_rounds`.

Значение должно иметь точный тип int и быть больше нуля.

### 7.2. BattleOutcome

Модуль: `battle_outcome.py`

Возможные исходы:
- `A_WON` — победил агент A;
- `B_WON` — победил агент B;
- `BOTH_LOST` — оба агента погибли;
- `BOTH_WON` — оба агента остались живы после достижения лимита раундов.

`BOTH_WON` означает завершение боя по лимиту, а не ничью в смысле отдельного состояния DRAW.

### 7.3. BattleRules

Модуль: `battle_rules.py`

BattleRules получает BattleSettings в конструкторе и определяет исход через `determine_outcome(...)`.

Порядок проверок:
1. Если оба агента мертвы — BOTH_LOST.
2. Если мёртв только A — B_WON.
3. Если мёртв только B — A_WON.
4. Если оба живы и достигнут max_rounds — BOTH_WON.
5. В остальных случаях возвращается None, то есть бой продолжается.

Проверяются типы двух флагов жизни и номера раунда. Отрицательный номер раунда вызывает ValueError.

## 8. BattleEngine

Модуль: `battle_engine.py`

`BattleEngine` — координатор полного жизненного цикла одного боя. Он связывает стратегии, правила действий, изменяемые объекты Agent и правила определения исхода. Сам движок не определяет, сколько урона наносит атака, и не принимает стратегических решений: он управляет порядком вызова соответствующих компонентов.

### 8.1. Ответственность и зависимости

Движок получает две зависимости в конструкторе:

- `ActionRulesRegistry` — по типу выбранного действия возвращает объект правил, который умеет рассчитать эффекты;
- `BattleRules` — определяет, продолжается ли бой или уже завершён, и какой исход ему присвоить.

Участники и стратегии передаются отдельно в каждый вызов `start_battle()`:

```python
engine = BattleEngine(
    action_rules=ActionRulesRegistry(),
    battle_rules=BattleRules(BattleSettings(max_rounds=10)),
)

result = engine.start_battle(
    agent_a=agent_a,
    agent_b=agent_b,
    strategy_a=strategy_a,
    strategy_b=strategy_b,
)
```

Такое разделение позволяет повторно использовать один движок в серии боёв. При этом для независимого нового боя необходимо передавать новые экземпляры Agent: предыдущий бой изменяет их текущие характеристики. Build можно повторно использовать, поскольку это неизменяемая исходная конфигурация.

### 8.2. Участники алгоритма

Во время боя взаимодействуют следующие объекты:

| Объект | Роль в алгоритме |
|---|---|
| `Agent` | Хранит изменяемые текущие характеристики участника |
| `AgentStrategy` | Выбирает действие на основании доступной ей перспективы |
| `AgentSnapshot` | Фиксирует характеристики в конкретный момент времени |
| `AgentPerspective` | Предоставляет стратегии снимок своего агента и снимок противника |
| `Action` | Описывает выбранный тип действия и цель |
| `ActionRulesRegistry` | Находит правила для выбранного ActionType |
| `ActionRules` | Рассчитывает эффекты действия, не изменяя Agent |
| `Effect` | Связывает изменение характеристики с получателем |
| `ActionResult` | Описывает числовое изменение одной характеристики |
| `BattleRules` | Определяет исход по состоянию участников и номеру раунда |
| `BattleResult` | Содержит итог боя и конечные снимки участников |

Ключевое разделение: стратегия выбирает намерение, правила действия рассчитывают последствия, движок применяет последствия, а BattleRules решает, завершён ли бой.

### 8.3. Алгоритм запуска боя: `start_battle()`

Метод принимает четыре аргумента:

- `agent_a` и `agent_b` — два изменяемых объекта участников;
- `strategy_a` и `strategy_b` — стратегии соответствующих участников.

Результат метода — объект `BattleResult`.

#### Этап 1. Проверка идентичности участников

Первой проверкой выполняется:

```python
if agent_a is agent_b:
    raise ValueError("An agent cannot fight itself")
```

Оператор `is` проверяет идентичность объектов, а не равенство их характеристик. Два разных Agent с одинаковыми Build могут сражаться друг с другом. Один и тот же экземпляр Agent нельзя передать в обе позиции: иначе изменения состояния A и B фактически затрагивали бы один объект, что разрушило бы модель двух участников.

На этом этапе движок не проверяет типы стратегий и всех остальных аргументов. Предполагается, что вызывающий код передаёт объекты корректных типов.

#### Этап 2. Инициализация номера раунда

```python
current_round = 0
```

Счётчик обозначает количество уже полностью завершённых раундов, а не номер раунда, который сейчас выполняется.

Следовательно:
- до начала боя сыграно 0 раундов;
- после завершения первого раунда счётчик становится равен 1;
- если бой завершается ещё до первого раунда, результат содержит `rounds_played == 0`.

#### Этап 3. Проверка начального состояния

Движок читает состояние жизни обоих участников:

```python
alive_a = agent_a.is_alive
alive_b = agent_b.is_alive
```

Свойство `Agent.is_alive` возвращает результат проверки текущего здоровья на условие `health > 0`.

Затем вызывается:

```python
outcome = self.__battle_rules.determine_outcome(
    agent_a_alive=alive_a,
    agent_b_alive=alive_b,
    current_round=current_round,
)
```

Это важная проверка до входа в цикл. Она позволяет корректно обработать участников, которые уже были мертвы до запуска боя:

| A жив | B жив | Результат до первого раунда |
|---|---|---|
| Да | Да | Бой продолжается, если лимит раундов ещё не достигнут |
| Нет | Да | `B_WON`, 0 раундов |
| Да | Нет | `A_WON`, 0 раундов |
| Нет | Нет | `BOTH_LOST`, 0 раундов |

При положительном `max_rounds` и начальном `current_round = 0` два живых участника переходят к первому раунду.

#### Этап 4. Условие продолжения цикла

```python
while outcome is None:
    ...
```

Цикл продолжается только тогда, когда BattleRules не смог определить исход боя и вернул `None`.

BattleEngine не дублирует внутри цикла условия победы и поражения. Решение о завершении централизовано в BattleRules. Это важно: если правила завершения изменятся, алгоритм цикла не должен содержать вторую независимую реализацию этих правил.

#### Этап 5. Создание снимков состояния в начале раунда

В начале каждой итерации движок получает два снимка:

```python
snapshot_a = agent_a.snapshot
snapshot_b = agent_b.snapshot
```

Каждый Snapshot содержит копию текущего словаря характеристик Agent, защищённую от изменения через `MappingProxyType`.

Снимки фиксируют состояние именно на начало текущего раунда. Они не являются живыми ссылками на изменяемые характеристики Agent. Если позднее Agent получит урон, ранее созданный Snapshot останется прежним.

Это обеспечивает единое исходное состояние для решений обоих участников. A не получает преимущество от того, что его стратегия вызывается первой, а B не принимает решение на основании уже изменённого состояния.

#### Этап 6. Создание перспектив участников

Из двух снимков создаются две перспективы:

```python
a_perspective = AgentPerspective(
    own_state=snapshot_a,
    enemy_state=snapshot_b,
)
b_perspective = AgentPerspective(
    own_state=snapshot_b,
    enemy_state=snapshot_a,
)
```

Содержимое перспектив:

| Перспектива | `own_state` | `enemy_state` |
|---|---|---|
| A | `snapshot_a` | `snapshot_b` |
| B | `snapshot_b` | `snapshot_a` |

Это два представления одного и того же состояния боя. Перспектива не копирует характеристики повторно: она ссылается на соответствующие неизменяемые снимки.

Стратегия получает только свою перспективу. Она не получает прямой доступ к изменяемому Agent и не может случайно изменить здоровье участника через штатный интерфейс этих объектов.

#### Этап 7. Одновременный по состоянию выбор действий

```python
action_a = strategy_a.choose_action(a_perspective)
action_b = strategy_b.choose_action(b_perspective)
```

Вызовы выполняются последовательно в коде: сначала стратегия A, затем стратегия B. Но обе стратегии получают снимки, сделанные до начала любых изменений текущего раунда.

Поэтому корректнее говорить не о параллельном выполнении Python-кода, а о синхронном выборе решений на основе одного состояния раунда.

На этом этапе:
- характеристики Agent ещё не изменены;
- стратегия A не видит результат действия B;
- стратегия B не видит результат действия A;
- обе стратегии возвращают Action, содержащий ActionType и Target.

В текущей реализации AgentStrategy выбирает первый элемент переданного ей списка доступных действий. Для ATTACK выбирается Target.ENEMY. Это поведение текущей заглушки стратегии, а не ограничение BattleEngine.

#### Этап 8. Получение правил для каждого действия

Для выбранных действий движок отдельно запрашивает правила:

```python
action_rule_a = self.__action_rules.get(action_a.action_type)
action_rule_b = self.__action_rules.get(action_b.action_type)
```

Registry выполняет отображение:

`ActionType → ActionRules`

Например, для `ActionType.ATTACK` возвращается экземпляр `AttackRules`.

Правила A и B запрашиваются отдельно, потому что участники могут выбрать разные типы действий. Если тип действия не зарегистрирован, текущая реализация Registry выбросит `KeyError`. BattleEngine не перехватывает эту ошибку.

#### Этап 9. Расчёт эффектов обоих действий

Движок вызывает правила каждого участника:

```python
effects_tuple_a = action_rule_a.calculate_effects(
    a_perspective,
    action_a.target,
)
effects_tuple_b = action_rule_b.calculate_effects(
    b_perspective,
    action_b.target,
)
```

Каждый вызов возвращает кортеж Effect. В нём может быть один или несколько эффектов, направленных на самого действующего агента или на противника.

Для текущей атаки расчёт выглядит так:

1. AttackRules читает DAMAGE из `state.own_state.attributes`.
2. Создаёт отрицательное значение изменения здоровья: `delta = -own_damage`.
3. Создаёт `ActionResult(Attribute.HEALTH, delta)`.
4. Оборачивает ActionResult в Effect с целью, выбранной стратегией.
5. Возвращает кортеж из одного Effect.

**Принципиальный момент:** `calculate_effects()` только рассчитывает последствия. Он не вызывает `Agent.apply_action_result()` и не изменяет состояние участников.

Сначала рассчитывается весь набор эффектов A, затем весь набор эффектов B. Только после успешного завершения обоих расчётов движок переходит к применению эффектов. Это означает, что оба набора рассчитаны на основе снимков начала раунда.

Если расчёт второго набора выбросит исключение, эффекты первого набора к агентам ещё не применены. Однако сам бой в таком случае завершится исключением, а не объектом BattleResult.

#### Этап 10. Применение эффектов участника A

```python
self.apply_effects(
    source_agent=agent_a,
    target_agent=agent_b,
    effects=effects_tuple_a,
)
```

Для каждого Effect метод `apply_effects()` определяет фактического получателя:

- `Target.SELF` означает `source_agent`, то есть A;
- `Target.ENEMY` означает `target_agent`, то есть B.

Затем вызывается:

```python
recipient.apply_action_result(effect.action_result)
```

Agent применяет дельту к указанной характеристике. Для здоровья действует верхнее ограничение, равное исходному `build.health`; нижнего ограничения в текущей версии нет.

Если в кортеже несколько эффектов, они применяются последовательно в порядке следования в кортеже. Каждый следующий эффект видит текущее значение характеристики после предыдущих эффектов этого же набора.

#### Этап 11. Применение эффектов участника B

После завершения применения эффектов A движок применяет набор B:

```python
self.apply_effects(
    source_agent=agent_b,
    target_agent=agent_a,
    effects=effects_tuple_b,
)
```

Правило определения получателя такое же, но источник и противник поменялись местами:

- `Target.SELF` означает B;
- `Target.ENEMY` означает A.

Важное следствие текущего алгоритма: если эффекты A обнулили здоровье B, уже выбранное и рассчитанное действие B всё равно применяется. Движок не проверяет `agent_b.is_alive` между применением наборов A и B.

Это намеренное свойство алгоритма одновременного раунда: оба действия определяются состоянием в начале раунда и оба разрешаются до проверки результата раунда.

При этом физическое применение не атомарно: сначала меняется состояние после эффектов A, затем после эффектов B. Если эффекты станут зависеть от промежуточного состояния или появятся побочные триггеры, порядок применения будет иметь значение.

#### Этап 12. Завершение раунда и обновление счётчика

Только после применения обоих наборов эффектов выполняется:

```python
current_round += 1
```

Следовательно, раунд засчитывается только после того, как движок завершил применение эффектов обоих участников.

Если во время расчёта или применения возникло исключение, метод не вернёт BattleResult. В частности, текущий код не реализует откат уже применённых изменений при исключении во время применения эффектов.

#### Этап 13. Повторная проверка состояния участников

После завершения раунда движок повторно читает свойства жизни:

```python
alive_a = agent_a.is_alive
alive_b = agent_b.is_alive
```

Эти значения уже отражают все эффекты обоих участников.

Затем BattleRules получает обновлённые флаги и актуальный номер раунда:

```python
outcome = self.__battle_rules.determine_outcome(
    agent_a_alive=alive_a,
    agent_b_alive=alive_b,
    current_round=current_round,
)
```

Порядок условий в BattleRules важен:

1. Если оба участника мертвы, результат — `BOTH_LOST`.
2. Если мёртв только A, результат — `B_WON`.
3. Если мёртв только B, результат — `A_WON`.
4. Если оба живы, но `current_round >= max_rounds`, результат — `BOTH_WON`.
5. Иначе возвращается `None`, и начинается следующий раунд.

Проверки смерти выполняются раньше проверки лимита. Поэтому если оба агента погибли именно в последнем разрешённом раунде, результатом будет `BOTH_LOST`, а не `BOTH_WON`.

#### Этап 14. Формирование BattleResult

Когда BattleRules возвращает не-None исход, цикл заканчивается. Движок создаёт итоговые снимки и возвращает:

```python
return BattleResult(
    outcome=outcome,
    rounds_played=current_round,
    agent_a_state=agent_a.snapshot,
    agent_b_state=agent_b.snapshot,
)
```

Итог содержит:
- определённый исход;
- число полностью завершённых раундов;
- финальное состояние A;
- финальное состояние B.

В BattleResult сохраняются Snapshot, а не ссылки на Agent. Поэтому дальнейшее изменение исходных объектов Agent не изменяет уже возвращённый результат.

### 8.4. Псевдокод полного алгоритма

Ниже приведена логика метода в сокращённой форме, без деталей создания объектов:

```text
START BATTLE
│
├─ Если A и B — один объект:
│    └─ Ошибка: агент не может сражаться сам с собой
│
├─ current_round = 0
│
├─ Проверить жизнь A и B
│
├─ Определить исход через BattleRules
│
└─ Пока исход не определён:
     │
     ├─ Снять snapshot A и snapshot B
     │
     ├─ Создать перспективу A:
     │    own = snapshot A
     │    enemy = snapshot B
     │
     ├─ Создать перспективу B:
     │    own = snapshot B
     │    enemy = snapshot A
     │
     ├─ Стратегия A выбирает Action A
     ├─ Стратегия B выбирает Action B
     │
     ├─ Получить ActionRules для Action A
     ├─ Получить ActionRules для Action B
     │
     ├─ Рассчитать эффекты A
     ├─ Рассчитать эффекты B
     │
     ├─ Применить эффекты A
     ├─ Применить эффекты B
     │
     ├─ current_round += 1
     │
     ├─ Проверить жизнь A и B
     ├─ Определить исход через BattleRules
     │
     └─ Если исход не определён — следующий раунд
     
├─ Создать финальные снимки A и B
│
└─ Вернуть BattleResult
```

### 8.5. Пример одного раунда с числами

Пусть в начале раунда:

| Характеристика | Агент A | Агент B |
|---|---:|---:|
| Здоровье | 7 | 5 |
| Урон | 3 | 5 |

Обе стратегии выбирают атаку по противнику.

**Шаг 1. Снимки.** Движок фиксирует A: (health=7, damage=3) и B: (health=5, damage=5).

**Шаг 2. Расчёт A.** AttackRules A читает урон 3 и формирует эффект: B получает изменение здоровья -3.

**Шаг 3. Расчёт B.** AttackRules B читает урон 5 и формирует эффект: A получает изменение здоровья -5.

На этом этапе состояние реальных Agent всё ещё не изменено.

**Шаг 4. Применение A.** B получает -3 здоровья: его здоровье становится 2.

**Шаг 5. Применение B.** A получает -5 здоровья: его здоровье становится 2.

**Шаг 6. Проверка.** Оба агента живы. Если лимит раундов не достигнут, BattleRules возвращает None, и начинается следующий раунд.

Теперь рассмотрим случай, когда у B в начале раунда было 4 здоровья, а у A — 5 урона. После применения эффекта A здоровье B станет -1, и B будет считаться мёртвым. Но эффект B всё равно будет применён к A, поскольку он был рассчитан до применения эффектов. Только после применения обоих наборов BattleRules определит итог: если A тоже мёртв — `BOTH_LOST`; если A жив — `A_WON`.

### 8.6. Гарантии и ограничения текущего алгоритма

**Что алгоритм гарантирует:**

- обе стратегии принимают решения на основе одного состояния начала раунда;
- эффекты обоих действий рассчитываются до изменения состояния Agent;
- погибший в текущем раунде участник всё равно завершает уже выбранное действие;
- проверка исхода выполняется после применения обоих наборов эффектов;
- число раундов увеличивается после полного разрешения раунда;
- результат содержит неизменяемые снимки конечного состояния;
- один BattleEngine может быть использован повторно с другими участниками.

**Чего алгоритм пока не гарантирует:**

- атомарного применения всех эффектов как единой транзакции;
- отката изменений, если применение одного из эффектов завершилось исключением;
- параллельного выполнения стратегий;
- проверки всех входных аргументов BattleEngine;
- автоматического создания новых Agent для серии экспериментов;
- сохранения истории каждого раунда.

Текущая схема подходит для простых аддитивных изменений характеристик. Если появятся эффекты, зависящие от промежуточного состояния, отражение урона, щиты, прерывание действий или триггеры смерти, модель разрешения раунда потребуется пересмотреть отдельно.
 
## 9. Результат боя

Модуль: `battle_result.py`

`BattleResult` — неизменяемый объект результата боя:
- `outcome` — BattleOutcome;
- `rounds_played` — количество сыгранных раундов;
- `agent_a_state` — итоговый AgentSnapshot участника A;
- `agent_b_state` — итоговый AgentSnapshot участника B.

Класс проверяет тип исхода, целочисленность и неотрицательность числа раундов, а также типы итоговых снимков. В результат не помещаются ссылки на изменяемые Agent.

## 10. Тестирование

Тесты расположены в `tests/`. Проверяются:
- допустимые и недопустимые сборки, неизменяемость Build;
- начальные характеристики Agent, изменение здоровья, смерть, лечение и верхнее ограничение здоровья;
- выбор действия стратегией;
- абстрактность ActionRules;
- определение исхода боя и валидация аргументов BattleRules;
- валидация и неизменяемость BattleResult;
- применение эффектов к себе и противнику, несколько эффектов;
- основные сценарии BattleEngine: победа A, победа B, гибель обоих, завершение по лимиту раундов и запрет боя агента с самим собой.

Для запуска полного набора:

```bash
uv run pytest
```

## 11. Текущие ограничения и технические замечания

Следующие пункты описывают состояние кода на момент подготовки документации и не являются утверждением, что эти функции уже реализованы:

1. **Нижняя граница здоровья.** Agent ограничивает здоровье сверху значением Build.health, но не ограничивает снизу нулём. Текущие тесты допускают отрицательное здоровье. Если игровое правило должно задавать диапазон от 0 до максимума, потребуется изменить реализацию и соответствующие тесты.
2. **Проверка AgentStrategy.** Пустой набор доступных действий не проверяется в конструкторе. При выборе действия это приведёт к IndexError.
3. **Валидация входов BattleEngine.** Сейчас явно проверяется только то, что agent_a и agent_b — разные объекты. Остальные аргументы не проверяются на тип в начале метода.
4. **Порядок применения эффектов.** Расчёт эффектов симметричен относительно снимков начала раунда, но применение последовательное. При появлении нелинейных эффектов, триггеров или зависимых от порядка правил может потребоваться отдельная модель атомарного разрешения раунда.
5. **Сохранение результатов.** BattleEngine возвращает BattleResult и не сохраняет его в файл или базу данных.
6. **Серии экспериментов.** Отдельного компонента для массового запуска боёв и агрегирования результатов пока нет.
7. **Обучение и подбор сборок.** Генерация сборок, оптимизация стратегий и обучение агентов пока не входят в реализованную функциональность.
8. **CLI.** Точка входа существует, но пока выполняет только демонстрационный вывод.

При изменении реализации этот документ следует обновлять вместе с тестами: документация должна отражать фактическое поведение кода, а не только предполагаемые будущие правила.
